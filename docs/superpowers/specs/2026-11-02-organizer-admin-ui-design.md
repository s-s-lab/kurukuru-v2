# Organizer Admin UI Design

## Intent

主催者がイベント作成時に発行された主催者用URLから安全にログインし、回答状況を把握しながらイベントの基本情報・通知設定・回答受付状態を管理できる画面を提供する。参加者画面と同じKurukuruの時間表中心の体験を保ちつつ、管理操作を誤りにくい一つの作業面へまとめる。

## Scope

- `#/events/:eventId/admin`を主催者管理画面として実装する。
- 管理パスワードで12時間管理セッションを発行する。
- 有効な管理セッションを同一タブの`sessionStorage`へ保存し、再読込時に管理状態を復元する。
- イベントタイトル、説明、回答通知設定を編集する。
- 回答受付を停止・再開する。
- 候補日時、確定日時、回答者、時間帯別回答数を管理者向けに表示する。
- 参加者用URLをコピーまたは共有できる。
- 通信中、成功、入力不正、通信失敗、期限切れ、受付停止の各状態を表示する。

## Non-goals

- 候補日時の追加・削除。
- 開催日時の確定・解除。
- イベントの論理削除。
- 主催者メールアドレス変更、メール認証、通知メール配送。
- 複数管理セッション一覧、明示的なサーバー側ログアウトAPI。
- 分析ダッシュボード、意味のないKPI、参加率スコア。

これらのライフサイクル操作は、管理画面の認証・状態管理が安定した後の独立した実装単位とする。

## Approaches considered

### 1. 一画面の管理ワークスペース（採用）

ログイン後は、回答状況を主領域、イベント設定を補助領域として同じページに配置する。PCは2カラム、モバイルは重要度順の縦積みとする。イベント規模が小さい現段階では、画面遷移を増やさず状態を把握しながら操作できる。

### 2. タブ型ダッシュボード

「回答」「設定」「候補日時」に分ける方式。将来機能は増やしやすいが、現在の機能量では情報が分断され、モバイルで状態確認と操作を往復するため採用しない。

### 3. 管理ウィザード

基本情報、回答確認、受付終了を順に進める方式。初期設定には適するが、日常的な確認・再編集には不向きなため採用しない。

## Information architecture

### Login state

ページの目的を「主催者用ページ」と明示し、イベントの存在を追加開示しないログインフォームを表示する。

- 管理用パスワード入力
- `管理画面を開く`ボタン
- パスワードの保存・再発行に関する誤解を招かない簡潔な補足
- 失敗時は固定文言と、取得できる場合だけrequest ID

イベントタイトルは認証成功前に表示しない。パスワードはReact stateだけに保持し、送信完了後またはアンマウント時に破棄する。

### Authenticated state

最初の表示領域で、ページの対象と主要操作が分かる構成にする。

1. 管理ヘッダー
   - `主催者用ページ`
   - イベントタイトル
   - `回答受付中`または`受付停止中`
   - 参加者用URLの共有操作
2. 回答状況（主領域）
   - 候補日の範囲
   - 確定日時。未確定時はその状態を明示
   - 時間グリッド上の候補枠と回答数
   - 回答者一覧（名前、コメント、更新日時）
   - 回答がない場合の空状態
3. イベント設定（補助領域）
   - タイトル
   - 説明
   - 回答時のメール通知
   - `変更を保存`
4. 受付状態
   - open時は`回答受付を停止`
   - closed時は`回答受付を再開`
   - 可逆操作であることを直近の説明で示す

## Visual direction

既存の`docs/design/direction.md`を優先し、「会議室のホワイトボードを、指で扱える精密な時間表にした道具」を管理画面にも適用する。

- 背景は白、見出しはDeep navy、主要操作はTeal、機能帯はPale aqua、罫線はBlue gray。
- 回答状況の時間グリッドを最大の視覚要素とし、設定カードを主役にしない。
- タイトル、受付状態、共有操作を一つのヘッダー帯にまとめる。
- 角丸は既存の8〜18pxに限定し、カード内カードを作らない。
- 受付停止は赤い危険操作として過剰に演出せず、navyのアウトラインと具体的な説明で区別する。イベント削除ではないため破壊的確認モーダルは使わない。
- 既存の記号と色を回答集計でも併用し、色だけに依存しない。

## Responsive behavior

### Desktop (901px以上)

- 最大幅1160pxの既存shellを使用する。
- 回答状況をおおむね2/3、設定を1/3とする2カラム。
- 設定領域はスクロール追従させず、ページ内の自然な順序を保つ。
- 時間グリッドは日付列を固定し、必要な場合だけ領域内で横スクロールする。

### Tablet and mobile (900px以下)

- 管理ヘッダー、受付状態、回答状況、イベント設定の順で縦積みにする。
- 共有操作と受付操作は幅いっぱいのボタンにする。
- 時間グリッドは既存参加者画面と同じ横スクロール表現を使う。
- 保存操作は入力フォームの末尾に置き、画面全体を覆う固定フッターにはしない。管理画面では回答表確認中に常時表示する必要がないためである。
- 320px幅で横方向のページ全体スクロールを発生させない。

## Client architecture

### `src/features/event-admin/admin-api.ts`

管理API境界を担当する。

- `createAdminSession(eventId, password, options)`
- `getAdminEvent(eventId, sessionToken, options)`
- `updateAdminEvent(eventId, sessionToken, request, options)`
- `closeAdminEvent(eventId, sessionToken, options)`
- `reopenAdminEvent(eventId, sessionToken, options)`
- 成功レスポンスをZodで検証し、API本文をそのまま例外文へ含めない。
- `AdminApiError`は`code`, `message`, `requestId`, `fieldErrors`, `status`だけを保持する。

### `src/features/event-admin/admin-session.ts`

ブラウザ内管理セッションを担当する。

- キーは`kurukuru:admin-session:<eventId>`。
- 保存値は`sessionToken`と`expiresAt`だけ。
- `expiresAt`が現在時刻以下、JSON不正、必要フィールド欠落なら読み取らず削除する。
- localStorage、URL、DOM、ログ、分析イベントへ保存しない。

### `src/pages/AdminEventPage.tsx`

ページ状態とユースケースを担当する。

- `checking-session` → `login` → `authenticated`の状態遷移を明示する。
- 保存済みセッションがあれば管理状態GETで検証する。
- `ADMIN_ACCESS_DENIED`では保存セッションを削除し、ログインへ戻して期限切れの説明を表示する。
- 基本情報保存、close/reopen成功時は返却された`AdminEvent`で単一状態を置き換える。
- 同時送信を抑止し、操作ごとに独立した進行・結果メッセージを持つ。

### Presentational components

- `AdminLoginForm.tsx`: パスワード入力とログイン状態。
- `AdminEventHeader.tsx`: タイトル、受付状態、共有。
- `AdminResponseOverview.tsx`: 時間帯集計と回答者一覧。
- `AdminEventSettings.tsx`: 基本情報・通知設定と受付操作。

表示コンポーネントはAPIやsessionStorageへ直接アクセスしない。

## Data derivation

- 候補枠は`date`, `slotIndex`順に表示する。
- 時間帯別集計は各候補枠について`best`, `ok`, `maybe`, `ng`の件数をクライアントで算出する。
- 回答者一覧はAPIの順序を維持し、名前・コメント・更新時刻を表示する。
- 確定日時は`[startSlot, endSlot)`を30分単位の表示時刻へ変換する。
- 集計値を評価スコアへ変換しない。

## Error and state handling

- ログイン失敗・期限切れ・不正セッションは、イベントの存在や上流詳細を示さない。
- 入力不正はフィールド近傍と要約へ表示する。
- 429はAPIの安全な文言を表示し、多重送信を避ける。
- ネットワーク障害と構造不正応答は`管理情報を読み込めませんでした。時間をおいて再度お試しください。`へ統一する。
- 変更成功は`aria-live="polite"`で通知する。
- 初期読込はレイアウトが大きく移動しない簡潔な読込状態を表示する。
- 回答0件は異常扱いせず、参加者用URLを共有する案内を表示する。

## Accessibility

- すべての入力に永続的なlabelを付ける。
- エラーは`aria-invalid`と`aria-describedby`で関連付ける。
- ボタンは最低44pxのタップ領域を確保する。
- 受付状態と回答区分は文字・記号・色を併用する。
- フォーカスリングは既存のTeal系3pxアウトラインを使う。
- 読込・保存・受付変更の結果を適切なlive regionで通知する。
- 通信中だけ関連ボタンを無効化し、ページ全体を操作不能にしない。
- 動きは必須にせず、追加する場合は`prefers-reduced-motion`に従う。

## Testing

### API client

- Bearerヘッダー、URL、メソッド、正規化されたリクエスト本文。
- セッション作成・管理状態・更新・close/reopenの成功レスポンス検証。
- 非JSON、構造不正成功、固定APIエラー、ネットワーク障害で秘密本文を露出しない。

### Session model

- イベント別キー、正常保存・復元、期限境界、JSON不正、別イベント分離。
- 保存文字列にパスワードが含まれない。

### Page integration

- 未ログイン表示とパスワード送信。
- 保存済み有効セッションの復元。
- 期限切れ・404時のセッション削除と再ログイン。
- 基本情報・通知設定の編集と成功/失敗。
- close/reopenと状態表示。
- 回答0件、複数回答、確定済み表示。
- 同時送信抑止、秘密情報非表示、参加者URL共有。
- ルート`/events/:eventId/admin`の接続。

## Success criteria

- 主催者用URLからパスワードでログインし、再読込しても同一タブ内では有効期限まで管理状態を復元できる。
- パスワードとセッショントークンがURL、DOM、ログ、localStorageへ現れない。
- 基本情報、通知設定、受付状態の変更がAPI応答と画面へ一貫して反映される。
- 候補枠・確定日時・回答状況をPCとモバイルで理解できる。
- 期限切れ時に安全にログインへ戻れる。
- キーボード操作、フォーカス表示、ラベル、live region、320px幅を含むレスポンシブ要件を満たす。
- 対象テスト、全体テスト、lint、TypeScript/Viteビルド、Functionビルド、Functionバンドル検査、差分検査が成功する。
