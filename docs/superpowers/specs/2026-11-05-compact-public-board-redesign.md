# Kurukuru コンパクト公開ボード再設計仕様

## 目的

Kurukuru を、長い説明ページや段階的な入力フローではなく、必要な情報と操作が一つの画面で把握できる時間単位の日程調整ツールへ再設計する。旧 URL と API の互換性を維持しながら、公開回答ボードを中心とする構成へ移行する。

## 設計原則

- モジュールと余白を小さくし、PC では主要操作を一画面に収める。
- 視認性は保ちつつ、装飾より操作と情報密度を優先する。
- 参加者の回答状況はパスワードなしで全員に公開する。
- 管理パスワードは候補日時の追加・変更・削除にのみ使う。
- 既存のイベント URL、管理 URL、API、回答編集トークンを維持する。

## トップ・イベント作成

- 大型ヒーローと「3つの手順」を廃止し、短い説明と作成フォームを主役にする。
- イベント作成は段階を分けず、一画面で完了する。
- PC は上段左にイベント名、メール、説明、管理パスワード、通知設定、上段右に2か月カレンダーを置く。
- 下段に時間帯一括指定と候補時間表を置き、右下に作成ボタンを置く。
- スマートフォンでは同じ内容を縦積みにし、候補時間表だけを横スクロールさせる。
- 入力エラーは該当項目の近くに表示し、イベント作成時に基本情報と候補日時を同時検証する。

## 公開回答ボード

- イベント概要、回答一覧、コメント、回答追加・編集の入口を同じ画面に置く。
- 回答一覧は回答者を行、候補時間を列とする表で表示する。
- 各回答は `◎ / ○ / △ / ×` で表示する。
- 回答者名の列は横スクロール時も固定する。
- 回答者名・コメント・回答内容は、公開 URL を知る全員が閲覧できる。
- 時間帯ごとの集計人数は表示しない。
- 回答追加・編集はモーダルで行い、公開ボードから画面遷移しない。
- 同じ端末では既存の回答編集トークンを再利用し、パスワードなしで回答を編集できる。
- 最大表示幅はおおむね 1440px とし、情報量が少ない場合も不自然に引き延ばさない。

## 候補日時管理

- 既存の `/events/:eventId/admin` URL を維持する。
- 管理画面は、管理パスワード認証後に候補日時の追加・変更・削除のみを提供する。
- 回答状況、イベント設定、日時確定、メール確認、削除などの独立した管理モジュールは表示しない。
- 公開回答ボードへ戻る導線を置く。

## メール通知

- 回答通知メールのリンク先を管理画面ではなく公開回答ボードにする。
- 「回答時にメール通知」が有効なイベントのみ、作成後に主催者確認メールを自動送信する。
- 通知が無効な場合は確認メールを送信しない。
- メール送信失敗でイベント作成自体を失敗扱いにしない。
- 既存のメール確認 URL と再送 API は互換性のため維持する。

## アクセシビリティと操作

- キーボードでカレンダー、時間表、モーダルを操作できる。
- モーダルには明確な見出し、閉じる操作、フォーカス復帰を実装する。
- 表の列・行見出しを保持し、記号だけでなく支援技術向けラベルを提供する。
- スクロール領域は時間表に限定し、ページ全体の横スクロールを発生させない。

## 完了条件

- 作成、公開閲覧、回答追加、同一端末での回答編集、候補日時編集が新 UI で完了できる。
- 公開ボードに全回答とコメントが表示され、時間帯別集計が存在しない。
- 既存の URL と API 契約が保たれる。
- 通知メールが公開ボードへ誘導する。
- 自動テスト、型検査、ビルドが成功し、PC・スマートフォン幅で主要画面を確認できる。
